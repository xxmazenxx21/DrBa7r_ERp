FRONTEND - WEEK 1, UPDATE 3
===========================

What is this?
-------------
The third round of backend changes, and the answers to your questions.
Read it AFTER doc/FRONTEND_WEEK1_READ_FIRST.txt and FRONTEND_WEEK1_UPDATE_2.txt.

What changed:
  1. Opening balance can be negative (customer AND supplier)       -> new
  2. A DELETED record can't be used as a reference anymore         -> BREAKING (small)
  3. A user's branch must be the same as their employee's branch   -> new 400
  4. Stricter validation: username, decimal places                 -> new 400s
  5. PATCH with null clears a field                                -> new
  6. Decisions for later weeks (no code change now)                -> read only

No database migration in this update. No route / field was renamed.

Every error still has { statusCode, message, error, code, field }.
Translate with "code" + "field" (see the Arabic messages in each part).


=====================================================================
PART 1 - Opening balance signs (رصيد أول المدة)
=====================================================================
openingBalance can now be NEGATIVE for suppliers too (customers already
could). It means:

  who        positive (+)                    negative (-)
  ---------  ------------------------------  -----------------------------------
  supplier   WE owe the supplier             the SUPPLIER owes us
             (علينا للمورد)                    (لنا عند المورد: دفعة مقدمة / مرتجع لم يُسترد)
  customer   the CUSTOMER owes us            WE owe the customer
             (على العميل لنا - مدين)          (للعميل علينا - دائن)

  0 (default) = nothing.

BEFORE:  POST /supplier { "name": "...", "openingBalance": -500 }
         -> 400 ["openingBalance must not be less than 0"]
AFTER:   POST /supplier { "name": "...", "openingBalance": -500 }
         -> 201, data.openingBalance = "-500"

Suggested UI: show the number without the sign plus a label, e.g.
"500 - لنا عند المورد" / "500 - علينا للمورد".
creditLimit is still minimum 0.


=====================================================================
PART 2 - Deleted references = DOES_NOT_EXIST
=====================================================================
Rule: an id in a request BODY that points to a deleted record is treated
exactly like an id that does not exist:
    400, code "DOES_NOT_EXIST", field = the field you sent.

Fields: categoryId, primaryItemUnitId (products), productId (stock),
employeeId, branchId (users + signup).

What changed:
  - POST/PATCH /users and POST /auth/signup: a DELETED employeeId / branchId
    was ACCEPTED before. Now:
      { "statusCode": 400, "message": "employeeId does not exist", "error": "Bad Request", "code": "DOES_NOT_EXIST", "field": "employeeId" }
      { "statusCode": 400, "message": "branchId does not exist", "error": "Bad Request", "code": "DOES_NOT_EXIST", "field": "branchId" }

  - POST /product-inventory/inventory/:inventoryId with a missing or deleted
    productId                                            (BREAKING: 404 -> 400)
      BEFORE: 404 { "message": "Product not found", "code": "NOT_FOUND", "field": null, ... }
      AFTER:  400 { "statusCode": 400, "message": "productId does not exist", "error": "Bad Request", "code": "DOES_NOT_EXIST", "field": "productId" }

  - Products (categoryId / primaryItemUnitId): no change, already worked so.

An id in the URL PATH (e.g. POST /inventory/branch/:branchId,
POST /employees/branch/:branchId, POST /product-inventory/inventory/:inventoryId,
GET /employees?branchId=) still answers 404 NOT_FOUND for missing AND deleted.

Suggested Arabic message (code DOES_NOT_EXIST):
    "<field label> غير موجود أو محذوف"   e.g.  "الفرع غير موجود أو محذوف"
Field labels: branchId = الفرع, employeeId = الموظف, productId = الصنف,
categoryId = التصنيف, primaryItemUnitId = الوحدة الأساسية
Suggested action: reload the dropdown list (the record was deleted meanwhile).


=====================================================================
PART 3 - User branch must match the employee's branch
=====================================================================
Applies to POST /users, PATCH /users/:id, POST /auth/signup.
A user linked to an employee is always in that employee's branch.

  you send                                     result
  -------------------------------------------  ---------------------------------------
  employeeId, no branchId                      201/200, branchId = employee's branch
  employeeId + the SAME branchId               201/200
  employeeId + a DIFFERENT branchId            400 (body below)
  PATCH branchId only, user has an employee    checked against that employee
  PATCH "employeeId": null                     unlinks the employee, branchId kept
  no employee                                  branchId is free (optional)

BEFORE:  POST /users { ..., "employeeId": "emp-in-cairo", "branchId": "alex" }
         -> 201 (user in Alex, employee in Cairo)
AFTER:   -> 400
         {
           "statusCode": 400,
           "message": "branchId must match the employee's branch",
           "error": "Bad Request",
           "code": "BAD_REQUEST",
           "field": "branchId"
         }

BEFORE:  POST /users { ..., "employeeId": "emp-in-cairo" }  -> branchId null
AFTER:   POST /users { ..., "employeeId": "emp-in-cairo" }  -> branchId "cairo"

Suggested UI: when the admin picks an employee, set the branch dropdown to the
employee's branch and disable it.
Suggested Arabic message (code BAD_REQUEST, field branchId, this message):
    "فرع المستخدم يجب أن يكون نفس فرع الموظف"

PART 4 - Validation limits (new 400s)
=====================================================================
All of these answer 400, code "VALIDATION_FAILED", "message" is an ARRAY,
"field" = the field.

4.1 username  (POST /users, PATCH /users/:id, POST /auth/signup)
    - 3 to 30 characters
    - only English letters A-Z a-z, digits 0-9, dot ".", underscore "_", dash "-"
    - NO spaces, no Arabic letters, no "@"
    - spaces at the start/end are removed (" ahmed " is saved as "ahmed")
    BEFORE:  "username": "ahmed ali"  -> 201
    AFTER:   "username": "ahmed ali"  -> 400
      { "statusCode": 400, "message": ["username must be 3-30 characters: letters, digits, dot, underscore or dash only (no spaces)"], "error": "Bad Request", "code": "VALIDATION_FAILED", "field": "username" }
    Suggested Arabic message:
      "اسم المستخدم من 3 إلى 30 حرفًا: حروف إنجليزية وأرقام و . _ - فقط بدون مسافات"
    Frontend check (same rule):  /^[A-Za-z0-9._-]{3,30}$/  after trim()
    Login is NOT checked with this rule (old accounts still log in); it only
    trims the spaces.

4.2 Decimal places  (too many -> 400, the server never rounds anymore)
    max 4: retailPrice, wholesalePrice, bulkWholesalePrice, reorderLimit
           (products), quantity, costPrice (product-inventory)
    max 2: creditLimit, openingBalance (customer), openingBalance (supplier)
    BEFORE:  "retailPrice": 12.34567  -> 201, saved as "12.3457"
    AFTER:   "retailPrice": 12.34567  -> 400
      { "statusCode": 400, "message": ["retailPrice must have at most 4 decimal places"], "error": "Bad Request", "code": "VALIDATION_FAILED", "field": "retailPrice" }
    BEFORE:  "openingBalance": 10.555 -> 201, rounded by the database
    AFTER:   "openingBalance": 10.555 -> 400 ["openingBalance must have at most 2 decimal places"]
    Suggested Arabic messages:
      4 places: "الحد الأقصى 4 أرقام بعد العلامة العشرية"
      2 places: "الحد الأقصى رقمان بعد العلامة العشرية"
    Suggested UI: limit the input (step="0.0001" / step="0.01").

4.3 Other limits (unchanged, listed so you have them all in one place)
    - password: min 6 characters
    - branch name, inventory name / address: min 2 characters
    - prices, quantity, costPrice, reorderLimit, creditLimit: min 0
    - openingBalance: no minimum (negative allowed)


=====================================================================
PART 5 - PATCH: null clears a field
=====================================================================
In every PATCH:
  - field NOT sent    -> unchanged
  - field sent null   -> CLEARED (saved as null), for these nullable fields:

      module      fields that null clears
      ----------  -------------------------------------------------
      branch      address
      customer    taxNumber, commercialRecord, phone, address
      supplier    taxNumber, contactPerson, phone, email
      employees   nationalId, jobTitle, hireDate
      products    barcode
      users       email, employeeId (unlinks), branchId (*)

      (*) branchId null is refused (400, Part 3) while the user has an employee.

  - null on ANY OTHER field -> 400 VALIDATION_FAILED (the field can't be empty),
    e.g. "name": null, "openingBalance": null, "role": null, "quantity": null.
    Send 0 for numbers you want to reset.

BEFORE:  PATCH /employees/:id { "hireDate": null }  -> 200, hireDate NOT changed
AFTER:   PATCH /employees/:id { "hireDate": null }  -> 200, data.hireDate = null

BEFORE:  PATCH /customer/:id { "creditLimit": null } -> 500 Internal server error
AFTER:   PATCH /customer/:id { "creditLimit": null } -> 400
  { "statusCode": 400, "message": ["creditLimit must not be less than 0", "creditLimit must be a number conforming to the specified constraints"], "error": "Bad Request", "code": "VALIDATION_FAILED", "field": "creditLimit" }

Suggested UI: when the user empties an optional text box, send null (not "")
so the value is really removed.

PART 6 - Decisions for later weeks (NO code change now)
=====================================================================
6.1 Roles
    Until Week 5 only SUPERADMIN can use the API (every other role gets 403).
    Keep ONE config map in the frontend:  role -> allowed pages, e.g.
        const ROLE_PAGES = { SUPERADMIN: ['*'], ADMIN: [], ACCOUNTANT: [], SALES: [], USER: [] };
    so opening pages per role in Week 5 is a one-place change.

6.2 Manual stock edit  (PATCH /product-inventory/:id)
    - Stays allowed after Week 2.
    - From Week 2 it will write an ADJUSTMENT stock movement and REQUIRE a
      "reason" field (plan a reason text box in the edit dialog now).
    - From Week 5 only SUPERADMIN / ADMIN may use it.

6.3 Postponed to the END of the project
    The backend does NOT prevent these yet, so the frontend must keep
    blocking them:
    - a user deleting themselves, or changing their own role
    - deleting or demoting the LAST SUPERADMIN
    - freeing employeeId / email when a user is deleted. Today a deleted user
      KEEPS them, so the same employee / email can't get a new account:
        { "statusCode": 409, "message": "employeeId belongs to a deleted user", "error": "Conflict", "code": "BELONGS_TO_DELETED", "field": "employeeId" }
      Suggested Arabic message:
        "هذا الموظف/البريد مرتبط بمستخدم محذوف"
