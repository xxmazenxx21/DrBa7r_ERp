Two readers:

Backend: run it locally with Docker (git pull origin main, then
docker compose up -d --build). Base URL: http://localhost:3000
Login: POST /auth/login { "username": "admin", "password": "admin123" }
-> data.access_token. Send it on EVERY request:  Authorization: Bearer <token>
Only SUPERADMIN users can call the API for now (any other role gets 403).

General API rules (they apply to everything below):
  - Every success response is   { "message": "...", "data": ... }
  - Every error response is     { "statusCode", "message", "error", "code", "field" }
    Translate errors with "code" (+ "field"), never by reading "message".
    "message" is a string, or an ARRAY of strings for validation errors.
  - Numbers are SENT as JSON numbers and RETURNED as STRINGS ("974.7", "10.6818").
    Use Number(value) before doing any math or comparing. Trailing zeros are
    not returned: 974.70 comes back as "974.7", 119.70 as "119.7".
  - Dates are SENT as "YYYY-MM-DD" and RETURNED as "YYYY-MM-DDT00:00:00.000Z":
    show the first 10 characters.
  - Unknown fields in a body or query string -> 400 "property X should not exist".
  - Delete is always a SOFT delete (the row is hidden, kept in the database).
  - In PATCH, a field not sent = unchanged; null CLEARS an optional text/date field
    (e.g. notes, validUntil, dueDate, reason); null on a required field -> 400.
  - "N" in a field name like "lines.N.quantity" is the line index, starting at 0:
    highlight row N+1 of the lines table.
  - Week 2 (purchasing, item card, units, currencies) is in doc/week2/week2flow.txt.
    Week 3 uses it as it is; the changes to old screens are in section 12.


=====================================================================
1. WHAT WEEK 3 IS
=====================================================================
Week 3 adds SALES (المبيعات) and STOCK CONTROL between warehouses (مراقبة المخزون):
  - three sales documents: quotation (عرض سعر بيع) -> invoice (فاتورة بيع)
    -> return (مرتجع بيع). They are the MIRROR of the Week 2 purchase
    documents, but the stock goes the OTHER way: a sale takes goods OUT,
    a sales return brings them back IN,
  - stock transfers (تحويل مخزني): goods move from one warehouse to another,
  - stock counts (جرد): the shelves are counted and the stock is set to what
    was counted (an adjustment for the difference).
The server computes every total, every cost and every stock change; the
frontend sends quantities, prices and percents and shows what the server returns.

The brush story (قصة الفرشة) - used everywhere in this file. It starts where
Week 2 ended:
  0. The Maadi warehouse (مخزن المعادي, فرع المعادي) has 218 brushes (فرشة)
     at an average cost of 10.6818. A carton (كرتونة) = 12 brushes.
  1. Customer "صيدلية الشفاء" gets a quotation: 5 cartons x 180, discount 5%,
     tax 14%:  subTotal 900 - discount 45 + tax 119.70 = netTotal 974.70
  2. It is accepted and converted into a CREDIT invoice (آجل); the customer
     pays 400 now -> remaining 574.70.
  3. We post the invoice: 60 brushes leave Maadi at 10.6818 each
     -> cost of goods sold 640.91, gross profit 855 - 640.91 = 214.09, Maadi 158.
  4. The customer returns 1 carton (تالف): 180 - 9 + 23.94 = netTotal 194.94.
     Posted: 12 brushes come back at the SAME 10.6818 they left with -> Maadi 170.
  5. We transfer 2 cartons Maadi -> Nasr City (مخزن مدينة نصر): Maadi 146, Nasr City 24.
  6. A stock count in Maadi finds 145 brushes: an adjustment of -1 -> Maadi 145.

    Maadi:     218 - 60 + 12 - 24 - 1 = 145   (9 movements on the item card)
    Nasr City:   0 + 24              =  24   (1 movement)

2. THE BIG PICTURE
=====================================================================

  SALES DOCUMENTS                                       stock effect
  ------------------------------------------------------------------------
  [Sales Quotation عرض سعر بيع]                         none (no effect at all)
     DRAFT -> SENT -> ACCEPTED
         |  convert-to-invoice (تحويل لفاتورة)
         v
  [Sales Invoice فاتورة بيع]  DRAFT                      none while DRAFT
         |  Post (ترحيل)                                 -60  (SALE) at the current average;
         |                                                    the cost is SAVED on the line
         |  Cancel (إلغاء)                               +60  (SALE_CANCEL) at the SAME cost
         v
  [Sales Return مرتجع بيع]  DRAFT (always linked         none while DRAFT
         |                  to a POSTED invoice)
         |  Post (ترحيل)                                 +12  (SALE_RETURN) at the sale cost
         |  Cancel (إلغاء)                               -12  (SALE_RETURN_CANCEL)
         v
  STOCK CONTROL
  ------------------------------------------------------------------------
  [Stock Transfer تحويل مخزني]  DRAFT                    none while DRAFT
         |  Post (ترحيل)   ONE step                      -24 in "from" (TRANSFER_OUT)
         |                                               +24 in "to"   (TRANSFER_IN), same cost
         |  Cancel (إلغاء)                               +24 back in "from" (TRANSFER_OUT_CANCEL)
         |                                               -24 out of "to"    (TRANSFER_IN_CANCEL)
  [Stock Count جرد]  DRAFT (the server makes the lines)  none while DRAFT
         |  type the counts (إدخال العد)                  none
         |  Post (ترحيل)   FINAL, no cancel              ADJUSTMENT = counted - balance (-1)
         v
  [Item card كارت الصنف]  shows every movement above, per product + warehouse,
                          in order, with the balance after each one

  Setup with the Week 1 screens: a second branch + warehouse (فرع / مخزن
  مدينة نصر) and a customer (عميل). Nothing else is new to set up.


=====================================================================
3. GLOSSARY
=====================================================================
  Document (مستند)            A paper with a number and a date: quotation, invoice,
                              return, transfer, count.
  Header / Lines (رأس / بنود)  ONE header row (customer, date, totals) + one line
                              per product (product, unit, quantity, price).
  Draft (مسودة)               Saved but has NO effect. Can be edited and deleted.
  Post (ترحيل)                Final confirmation: the stock moves and the document is locked.
  Cancel (إلغاء)              Reverses a posted document with an opposite stock movement.
                              The document stays, marked CANCELLED (ملغي), read only.
                              A stock count has NO cancel.
  Customer (العميل)            Who we sell to (Week 1 screen, GET /customer).
  Selling price (سعر البيع)    unitPrice: the price of ONE line unit (180 a carton). The
                              user types it; suggest it from the product's retailPrice /
                              wholesalePrice. No price level per customer.
  Cost of goods sold          totalCost of a sales invoice: what the goods cost us
  (تكلفة البضاعة المباعة)        (pieces x the average cost when they left).
  Gross profit (مجمل الربح)    (subTotal - discountValue) x exchangeRate - totalCost.
                              Shown on GET /sales-invoices/:id, never stored.
  Unit cost (تكلفة القطعة)      stockUnitCost / unitCost: the cost of ONE piece, set by the
                              server, never sent by the frontend.
  Base unit / Factor          Stock is always counted in the product's PRIMARY unit
  (الوحدة الأساسية / المعامل)    (piece قطعة). A carton with factor 12 = 12 pieces.
                              baseQuantity = quantity x factor = pieces.
  Returnable (المتبقي للإرجاع)  per invoice line: sold - already returned (POSTED returns).
  Transfer (تحويل مخزني)        Goods from one warehouse (من مخزن) to another (إلى مخزن),
                              in ONE step: no "in transit" (في الطريق).
  Stock count (جرد)            Counting the shelves. systemQuantity (الكمية في السيستم) =
                              what the system said when the count was opened;
                              countedQuantity (الكمية الفعلية) = what was counted;
                              difference (الفرق) = what posting changed.
  Stock movement (حركة مخزن)   One line for every stock in (+) or out (-). Never edited
                              or deleted. sourceType + sourceCode say which document made it.
  Item card (كارت الصنف)        All movements of one product in one warehouse, in order,
                              with the balance after each one.
  Average cost (متوسط التكلفة)  The cost of one piece after mixing old and new stock
                              (weighted average). Stock IN changes it; stock OUT does not.

4. THE DECISIONS AND THE RULES OF THE WEEK (and what they mean for the UI)
=====================================================================
The 6 decisions (taken by the owner; they don't change without asking):
  1. Stock transfer = ONE step. Posting takes the goods out of the source
     warehouse and puts them into the destination in the same transaction.
     UI: no "received" (استلام) button and no "in transit" status.
  2. A sales return MUST be linked to a POSTED sales invoice (salesInvoiceId
     required); the goods come back at the original sale cost.
     UI: no "return without invoice" mode (unlike purchase returns).
  3. A stock count goes DRAFT -> POSTED only. No cancel: a mistake is fixed
     with a new count. UI: no Cancel button on counts; confirm before posting.
  4. Sales price: the user sends unitPrice; the frontend suggests it from the
     product. No price level per customer.
  5. Selling below cost is allowed, with no warning (grossProfit may be negative).
  6. creditLimit (الحد الائتماني) is NOT checked until Week 4.

The 5 rules:
  1. Stock is always in the PRIMARY unit (pieces), even when you sell in cartons.
     UI: show quantities in the line's unit on documents (5 cartons), but show
     stock / item card / stock count numbers in pieces (60, 146).
  2. Only the server changes stock; every change is a stock movement.
     UI: refresh stock screens after every post / cancel.
  3. The server computes ALL totals and ALL costs.
     UI: you may preview totals while typing, but always display the values
     from the server response after saving. Never send totals, costs, codes,
     statuses or user ids (400 "property X should not exist").
  4. A POSTED document is never edited or deleted, only cancelled. Exception:
     a stock count has no cancel.
     UI: POSTED and CANCELLED documents are READ ONLY.
  5. NEW: the cost of a sale never comes from the user. It comes from the
     stock when the goods leave (the average cost at that moment) and is saved
     on the line (stockUnitCost). Anything that comes back into stock (invoice
     cancel, sales return, transfer cancel) comes back at the SAME cost it
     left with, not at today's average.

7. LINKS BETWEEN DOCUMENTS AND THE BLOCKS
=====================================================================
7.1 Sales quotation -> Sales invoice (convert-to-invoice)
  - Only an ACCEPTED quotation. The invoice copies customer, branch, warehouse
    (unless you send one), lines (unitPrice), discounts, tax and notes, in the
    default currency (rate 1), no dueDate.
  - The quotation becomes CONVERTED (convertedToInvoiceId); the invoice shows
    convertedFromQuotation { id, code } (null for a direct invoice). Show both as links.
  - The invoice is a normal DRAFT: edit payment, dueDate... before posting.
  - DELETE of that DRAFT invoice frees the quotation (same transaction): it
    goes back to ACCEPTED, convertedToInvoiceId = null, and can be converted
    again (a NEW SI number).
  - CANCEL of the POSTED invoice does NOT: the quotation stays CONVERTED and
    still points to the cancelled invoice (the history is kept).

7.2 Sales invoice -> Sales returns
  - GET /sales-invoices/:id lists salesReturns [{ id, code, returnDate, status, netTotal }]
    (not deleted, any status; [] when none).
  - GET /sales-invoices/:id/returnable gives, per invoice line (in the line's
    unit): quantity (sold), returnedQuantity (POSTED returns only), remainingQuantity
    = the most a new return can take.
  - A return line points to an invoice line with salesInvoiceLineId. Product,
    unit, price, the discount share, the tax and the cost come from the invoice.
  - GET /sales-returns/:id has salesInvoice { id, code, invoiceDate, status }: show it as a link.

7.3 Item card -> documents
  - Every movement made by a document has sourceType (SI / SR / ST / SC, and
    PI / PR from Week 2), sourceId (the document id) and sourceCode (its number):
    show sourceCode as a link to the document. A stock count writes ADJUSTMENT
    (تسوية) with sourceType "SC": show "تسوية جرد" + sourceCode.

7.4 The blocks (what the server refuses, and the error)
  - Cancel a sales invoice that has a POSTED return
      -> 400 BAD_REQUEST field "status" -> "ألغِ المرتجع أولًا"
  - Return more than sold minus already returned
      -> 400 QUANTITY_EXCEEDED field "lines.N.quantity" -> "الكمية المرتجعة أكبر من المتبقي من الفاتورة"
  - Return on an invoice that is not POSTED (DRAFT / CANCELLED)
      -> 400 BAD_REQUEST field "salesInvoiceId" "salesInvoiceId must be a POSTED invoice (this one is CANCELLED)"
  - Post a sales invoice / a transfer when the source warehouse doesn't have the pieces
      -> 400 INSUFFICIENT_STOCK field "lines.N.quantity" -> "الكمية المتاحة في المخزن غير كافية"
  - Cancel a sales return whose goods were sold again, or a transfer whose
    destination already sold / moved the goods
      -> 400 INSUFFICIENT_STOCK field "lines.N.quantity" (nothing changes)
      e.g. "Insufficient stock: available 0, requested 12"
  - Transfer to the same warehouse -> 400 BAD_REQUEST field "toWarehouseId"
  - Transfer a SERVICE product (خدمي) -> 400 BAD_REQUEST field "lines.N.productId"
    (SERVICE lines on sales invoices are allowed: no stock, cost 0)
  - Open a count on a warehouse with nothing to count -> 400 BAD_REQUEST field "warehouseId"
  - Post a count with no counted line -> 400 BAD_REQUEST field "lines"
  - Change the warehouse of a count -> 400 VALIDATION_FAILED "property warehouseId should not exist"
  - Delete a customer used by any (not deleted) sales invoice
      -> 400 BAD_REQUEST field null "Customer is used by N sales invoice(s) and cannot be deleted"
         -> "لا يمكن حذف العميل لأن عليه فواتير بيع"
  - Delete a currency used by sales invoices
      -> 400 BAD_REQUEST field null "Currency is used by N sales invoice(s) and cannot be deleted"
         -> "لا يمكن حذف العملة لأنها مستخدمة في فواتير بيع"
  - Delete a CONVERTED quotation -> 409 INVALID_STATUS "A CONVERTED quotation can't be deleted"

=====================================================================
9. HOW THE SERVER COMPUTES THE TOTALS AND THE COSTS
=====================================================================
  Totals (quotations, invoices, returns) - the same formulas as Week 2:
  lineTotal     = quantity x unitPrice - line discount                (4 decimals)
                  line discount = discountPercent % of it, OR a fixed discountValue (not both)
  subTotal      = sum of lineTotal                                    (2 decimals)
  discountValue = subTotal x discountPercent / 100
                  (if discountPercent is 0 or not sent: the fixed discountValue you send)
  taxValue      = (subTotal - discountValue) x taxPercent / 100
  netTotal      = subTotal - discountValue + taxValue
  Rounding: half up.

  Brush quotation / invoice: 5 x 180 = 900; discount 5% = 45; tax 14% of 855 = 119.70; net 974.70.

  Invoice payment:  CASH   -> paidAmount = netTotal, remainingAmount 0
                    CREDIT -> paidAmount 0 .. netTotal (default 0; switching CASH -> CREDIT
                              without paidAmount sets it to 0), remainingAmount = netTotal - paidAmount
  Currency:         not sent -> the default (exchangeRate 1); another currency -> exchangeRate required.

  Sales return (always from the invoice):
    unitPrice     = invoice lineTotal / invoice quantity        (180 a carton)
    lineTotal     = quantity x unitPrice                        (1 x 180 = 180)
    discountValue = subTotal x invoice discountValue / invoice subTotal   (180 x 45 / 900 = 9)
    discountPercent and taxPercent shown = the invoice's (5, 14)
    taxValue      = (subTotal - discountValue) x invoice taxPercent / 100 (171 x 14% = 23.94)
    netTotal      = 180 - 9 + 23.94 = 194.94
    refundAmount  = 0 .. netTotal (default 0): what we pay the customer back now

  Costs (set by the server when POSTING, never sent by the frontend):
    Sales invoice POST:  per STOCK line, the pieces leave at the warehouse AVERAGE now:
                         stockUnitCost = that average             (10.6818)
                         lineCost      = baseQuantity x stockUnitCost (60 x 10.6818 = 640.91)
                         totalCost     = sum of lineCost          (640.91)
                         SERVICE lines: no stock, cost 0.
    grossProfit       = (subTotal - discountValue) x exchangeRate - totalCost
                         (900 - 45) x 1 - 640.91 = 214.09; null while DRAFT; may be negative.
    Sales invoice CANCEL: the pieces come back at the SALE movement's unitCost.
    Sales return POST:   pieces back at the invoice line's stockUnitCost (12 x 10.6818 = 128.18)
                         -> lineCost, totalCost (تكلفة البضاعة الراجعة).
    Sales return CANCEL: pieces out at the warehouse's CURRENT average.
    Transfer POST:       out of "from" at its average; into "to" at that SAME cost
                         unitCost 10.6818, totalCost = 24 x 10.6818 = 256.36 (قيمة التحويل).
    Transfer CANCEL:     out of "to" at its current average; back into "from" at the
                         TRANSFER_OUT unitCost.
    Stock count POST:    ADJUSTMENT of (countedQuantity - the balance at posting) at the
                         current average; the average never changes. Saved per line:
                         difference (-1) and unitCost (10.6818).
    New average after any stock IN: (old qty x old avg + in qty x in cost) / (old qty + in qty).
    Stock OUT never changes the average.

  The frontend must NOT send (the server rejects them: 400 "property X should not exist"):
    - totals: subTotal, taxValue, netTotal, remainingAmount, lineTotal, baseQuantity, unitFactor
    - costs: stockUnitCost, lineCost, totalCost, unitCost (transfers), difference / unitCost (counts),
      grossProfit
    - codes and statuses: code, status (status changes only via the action endpoints)
    - user ids: createdBy, modifiedBy, postedBy, cancelledBy (taken from the token)
    - on a sales return: discountPercent, discountValue, taxPercent (from the invoice);
      productId / itemUnitId / unitPrice in a return line are accepted but IGNORED
    - on a stock count: lines (on create), systemQuantity, warehouseId (on PATCH)
  Limits: quantities and prices max 4 decimals; money (paidAmount, refundAmount,
  header discountValue) max 2; percents 0-100 with max 2 decimals; countedQuantity >= 0.
  Too many decimals -> 400 VALIDATION_FAILED (the server never rounds your input).

10. LISTS
=====================================================================
Paginated lists take ?page=1&pageSize=20 (page >= 1, pageSize 1-100, default 20)
and return data as an OBJECT:
  { "items": [ ... ], "meta": { "page": 1, "pageSize": 20, "total": 1, "totalPages": 1 } }
A page after the last one returns "items": [] (not an error).
Bad page / pageSize / filter value / unknown parameter -> 400 VALIDATION_FAILED.

  list                         paginated  filters (all optional)
  ---------------------------  ---------  ---------------------------------------------------------------
  GET /sales-quotations         yes        customerId, branchId, status, dateFrom, dateTo, search
                                           (search = part of the code, the customer name or the notes)
  GET /sales-invoices           yes        customerId, branchId, warehouseId, status, paymentType,
                                           dateFrom, dateTo, search (code, customer name, notes)
  GET /sales-returns            yes        customerId, salesInvoiceId, status, dateFrom, dateTo
  GET /stock-transfers          yes        fromWarehouseId, toWarehouseId, status, dateFrom, dateTo,
                                           search (code or notes)
  GET /stock-counts             yes        warehouseId, status, dateFrom, dateTo
  GET /stock-movements          yes        productId, warehouseId, type, dateFrom, dateTo (newest first;
                                           the dates filter movementDate = when it was posted)
  GET /stock-movements/item-card NO        productId + warehouseId REQUIRED (one object, movements oldest first)
  GET /sales-invoices/:id/returnable NO    - (one object with lines)
  Week 1 lists (/customer, /branch, /inventory, /products...)  NO (plain arrays)

  Document lists: newest document date first. dateFrom / dateTo: "YYYY-MM-DD",
  both inclusive, on the document date (quotationDate / invoiceDate /
  returnDate / transferDate / countDate). Each item = the header +
  "_count": { "lines": N } and NO lines (open one document with GET /:id):
    quotations: + customer, branch, warehouse, isExpired
    invoices:   + customer, branch, warehouse, currency (NO grossProfit in the list)
    returns:    + customer, branch, warehouse, salesInvoice { id, code }
    transfers:  + fromWarehouse / toWarehouse { id, name, branch { id, code, name } }
    counts:     + warehouse { id, name, branch { id, code, name } }
