Authentication & Authorization API Documentation
================================================

Base URL
--------
Production:      https://drba7rerp-production.up.railway.app
Local (Docker):  http://localhost:3000

Overview
--------
The backend is secured globally with JWT. Every endpoint requires a valid
Bearer token AND the SUPERADMIN role, EXCEPT:
    POST /auth/signup   (public, TEMPORARY)
    POST /auth/login    (public)
    POST /users/login   (public, identical to /auth/login)

First account on a fresh (Docker) database:
    username: admin
    password: admin123
    role:     SUPERADMIN

How to Authenticate
-------------------
Log in, take "data.access_token" from the response, and send it on every
request:

    Authorization: Bearer <access_token>


---------------------------------------------------------
AUTH APIs
---------------------------------------------------------

1) Signup  ** TEMPORARY - will be removed before production **
   Method: POST
   URL: /auth/signup
   Access: Public (no token needed)
   Description: Creates a new account. The account is ALWAYS a SUPERADMIN,
                whatever role you send. The password is stored hashed and is
                never returned.

   Validation Rules:
   - username: required, 3-30 characters, only letters (A-Z a-z), digits,
               dot (.), underscore (_), dash (-). NO spaces. Trimmed. Unique.
   - password: required string, minimum 6 characters
   - email: optional, valid email (must be unique)
   - employeeId: optional string (id of an ACTIVE employee)
   - branchId: optional string (id of an ACTIVE branch). With an employeeId it
               is filled from the employee; a different branch -> 400
               (same branch rule as POST /users, see users.txt)
   - role: optional, one of SUPERADMIN | ADMIN | ACCOUNTANT | SALES | USER
           (accepted but IGNORED - the user is always SUPERADMIN)

   Request Example:
   {
     "username": "drba7r",
     "password": "drba7r12345",
     "email": "drba7r@example.com"
   }

   Response Example (201 Created):
   {
     "message": "User signed up successfully",
     "data": {
       "id": "cmwpqmbpt000e2fleknaahyq0",
       "username": "drba7r",
       "email": "drba7r@example.com",
       "role": "SUPERADMIN",
       "employeeId": null,
       "branchId": null,
       "lastLoginDate": null,
       "createdAt": "2026-11-21T01:36:50.897Z",
       "updatedAt": "2026-11-21T01:36:50.897Z"
     }
   }

   Error Response (409 - username or email already used by an ACTIVE user):
   {
     "statusCode": 409,
     "message": "username already exists",
     "error": "Conflict",
     "code": "ALREADY_EXISTS",
     "field": "username"
   }
   (or "email already exists" / "employeeId already exists")

   Error Response (409 - username / email / employeeId belongs to a DELETED user):
   {
     "statusCode": 409,
     "message": "username belongs to a deleted user",
     "error": "Conflict",
     "code": "BELONGS_TO_DELETED",
     "field": "username"
   }

   Error Response (400 - employeeId / branchId does not exist or is deleted):
   {
     "statusCode": 400,
     "message": "branchId does not exist",
     "error": "Bad Request",
     "code": "DOES_NOT_EXIST",
     "field": "branchId"
   }

   Error Response (400 - validation / unknown field):
   {
     "statusCode": 400,
     "message": ["Password must be at least 6 characters long"],
     "error": "Bad Request",
     "code": "VALIDATION_FAILED",
     "field": "password"
   }

   Error Response (400 - bad username, e.g. "ahmed ali"):
   {
     "statusCode": 400,
     "message": ["username must be 3-30 characters: letters, digits, dot, underscore or dash only (no spaces)"],
     "error": "Bad Request",
     "code": "VALIDATION_FAILED",
     "field": "username"
   }

   Error Response (400 - branchId different from the employee's branch):
   {
     "statusCode": 400,
     "message": "branchId must match the employee's branch",
     "error": "Bad Request",
     "code": "BAD_REQUEST",
     "field": "branchId"
   }

2) Login
   Method: POST
   URL: /auth/login        (POST /users/login is identical)
   Access: Public (no token needed)
   Description: Checks username/password, updates the user's lastLoginDate,
                and returns a JWT plus the user's id, username and role.

   Validation Rules:
   - username: required string (spaces at the start/end are trimmed; the
               3-30 characters rule is NOT checked here, so old accounts can
               still log in)
   - password: required string

   Request Example:
   {
     "username": "admin",
     "password": "admin123"
   }

   Response Example (201 Created):
   {
     "message": "Logged in successfully",
     "data": {
       "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
       "user": {
         "id": "92c91eff-edfe-4606-b1a6-d59df502e8a6",
         "username": "admin",
         "role": "SUPERADMIN"
       }
     }
   }

   Use data.user.role to know if the account is SUPERADMIN. Right now only
   SUPERADMIN can use the rest of the API (every other role gets 403).

   Error Response (401 - wrong username/password, or user is deleted):
   {
     "statusCode": 401,
     "message": "Invalid credentials",
     "error": "Unauthorized",
     "code": "UNAUTHORIZED",
     "field": null
   }

   Error Response (400 - missing fields):
   {
     "statusCode": 400,
     "message": ["username should not be empty", "username must be a string"],
     "error": "Bad Request",
     "code": "VALIDATION_FAILED",
     "field": "username"
   }


---------------------------------------------------------
Roles
---------------------------------------------------------
    SUPERADMIN | ADMIN | ACCOUNTANT | SALES | USER

The role is in the login response (data.user.role) and inside the JWT payload
({ sub, username, role }).
Current rule: EVERY endpoint (except signup/login) requires SUPERADMIN.
Per-endpoint roles will be opened up later; the docs will say so.


---------------------------------------------------------
Frontend Integration Guide
---------------------------------------------------------

1. Missing / invalid token (401)
   {
     "statusCode": 401,
     "message": "Unauthorized",
     "error": "Unauthorized",
     "code": "UNAUTHORIZED",
     "field": null
   }
   Action: intercept 401 in your Axios/Fetch client, clear the session,
   and redirect to the Login screen.

2. Role not allowed (403)
   Any logged-in user that is NOT SUPERADMIN gets this on every endpoint:
   {
     "statusCode": 403,
     "message": "You do not have the required roles to access this resource",
     "error": "Forbidden",
     "code": "FORBIDDEN",
     "field": null
   }
   Action: show a "Permission Denied" toast/alert.

3. Token lifetime
   Tokens are valid for a very long time (3650 days), so in practice the user
   stays logged in until they log out (delete the token on the frontend).
