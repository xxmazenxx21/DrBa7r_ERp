DrBa7r ERP - WEEK 2 FLOW (purchasing + stock), start to finish
==============================================================

This file is SELF-CONTAINED: you can understand and build the whole Week 2
frontend from it alone. Every term has its Arabic screen label next to it,
e.g. Post (ترحيل). Every request, field, status rule and error below was
checked against the backend code.

Backend: run it locally with Docker (git pull origin main, then
docker compose up -d --build). Base URL: http://localhost:3000
Login: POST /auth/login { "username": "admin", "password": "admin123" }
-> data.access_token. Send it on EVERY request:  Authorization: Bearer <token>
Only SUPERADMIN users can call the API for now (any other role gets 403).

General API rules (they apply to everything below):
  - Every success response is   { "message": "...", "data": ... }
  - Every error response is     { "statusCode", "message", "error", "code", "field" }
    Translate errors with "code" (+ "field"), never by reading "message".
    "message" is a string, or an ARRAY of strings for validation errors.
  - Numbers are SENT as JSON numbers and RETURNED as STRINGS ("1539", "10.6818").
    Use Number(value) before doing any math or comparing.
  - Dates are SENT as "YYYY-MM-DD" and RETURNED as "YYYY-MM-DDT00:00:00.000Z":
    show the first 10 characters.
  - Unknown fields in a body or query string -> 400 "property X should not exist".
  - Delete is always a SOFT delete (the row is hidden, kept in the database).
  - In PATCH, a field not sent = unchanged; null CLEARS an optional text/date field
    (e.g. notes, validUntil, dueDate, reason); null on a required field -> 400.


=====================================================================
1. WHAT WEEK 2 IS
=====================================================================
Week 2 adds PURCHASING (المشتريات) and real STOCK TRACKING (المخزون):
  - currencies (العملات) and product units (وحدات الصنف: carton = 12 pieces),
  - every stock change is recorded as a stock movement (حركة مخزن), so each
    product has an item card (كارت الصنف) and a weighted average cost,
  - three purchase documents: quotation (عرض سعر) -> invoice (فاتورة) -> return (مرتجع).
The server computes every total and every stock change; the frontend sends
quantities, prices and percents and shows what the server returns.

The brush example (فرشة) - used everywhere in this file:
  1. The Maadi warehouse (مخزن المعادي) has 100 brushes at 10 each.
  2. Supplier "النيل" sends a quotation: a carton (12 brushes) costs 150.
  3. We buy 10 cartons, discount 10%, tax 14%:
       subTotal 1500 - discount 150 + tax 189 = netTotal 1539
  4. We post the invoice: +120 brushes, each costs 1500 x 0.9 / 120 = 11.25
       stock 220, average cost (100 x 10 + 120 x 11.25) / 220 = 10.6818
  5. 2 cartons are broken: a return of 2 cartons = 300 - 30 + 37.80 = netTotal 307.80
  6. We post the return: -24 brushes -> stock 196, average still 10.6818.

2. THE BIG PICTURE
=====================================================================

  SETUP (once)                                         stock effect
  ------------------------------------------------------------------------
  [Currency العملة]  EGP = default (العملة الأساسية)     none
         |
  [Product units وحدات الصنف]  brush: carton = 12      none
         |
  [Opening stock رصيد افتتاحي]  POST /product-inventory  +100  (OPENING)
         |
  DOCUMENTS (every day)
  ------------------------------------------------------------------------
  [Purchase Quotation عرض سعر شراء]                     none (no effect at all)
     DRAFT -> SENT -> ACCEPTED
         |  convert-to-invoice (تحويل لفاتورة)
         v
  [Purchase Invoice فاتورة شراء]  DRAFT                  none while DRAFT
         |  Post (ترحيل)                                 +120  (PURCHASE), new average
         |  Cancel (إلغاء)                               -120  (PURCHASE_CANCEL)
         v
  [Purchase Return مرتجع شراء]  DRAFT                    none while DRAFT
         |  Post (ترحيل)                                 -24   (PURCHASE_RETURN), average unchanged
         |  Cancel (إلغاء)                               +24   (PURCHASE_RETURN_CANCEL)
         v
  [Item card كارت الصنف]  shows every movement above, in order, with the balance after each

  Manual stock edit (تسوية) at any time: PATCH /product-inventory/:id
  -> ADJUSTMENT movement with the difference (needs a reason).


=====================================================================
3. GLOSSARY
=====================================================================
  Document (مستند)          A paper with a number and a date: quotation, invoice, return.
  Header / Lines (رأس / بنود) A document is ONE header row (supplier, date, totals) +
                            one line per product (product, unit, quantity, price).
  Draft (مسودة)             Saved but has NO effect. Can be edited and deleted.
  Post (ترحيل)              Final confirmation: the stock moves and the document is locked.
  Cancel (إلغاء)            Reverses a posted document with an opposite stock movement.
                            The document stays, marked CANCELLED (ملغي), read only.
  Base unit / Factor        Stock is always counted in the product's PRIMARY unit
  (الوحدة الأساسية / المعامل)  (e.g. piece قطعة). A carton with factor 12 = 12 pieces.
  Stock movement (حركة مخزن) One line for every stock in (+) or out (-). Never edited or deleted.
  Item card (كارت الصنف)     All movements of one product in one warehouse, in order,
                            with the balance after each one.
  Average cost (متوسط التكلفة) The cost of one piece after mixing old and new stock
                            (weighted average). Stock in changes it; stock out does not.
  Exchange rate (سعر الصرف)  How many default-currency units (EGP) one unit of the
                            invoice's currency is worth on the invoice date. Stock is
                            always valued in the default currency.


=====================================================================
4. THE 4 RULES OF THE WEEK (and what they mean for the UI)
=====================================================================
  1. Stock is always in the PRIMARY unit (pieces), even when you buy in cartons.
     UI: show quantities in the line's unit on documents (10 cartons), but show
     stock / item card numbers in pieces (120). baseQuantity = pieces.
  2. Only the server changes stock; every change is a stock movement.
     UI: there is NO "create movement" screen. Stock changes only through:
     opening stock, manual adjustment, posting / cancelling invoices and returns.
     Refresh stock screens after those actions.
  3. The server computes ALL totals.
     UI: you may show a live preview while typing, but always display the
     totals from the server response after saving. Never send subTotal,
     discountValue (except a fixed discount, see section 9), taxValue,
     netTotal, remainingAmount, lineTotal, baseQuantity, unitFactor, code,
     status, createdBy...
  4. A POSTED document is never edited or deleted, only cancelled.
     UI: when status is POSTED or CANCELLED, show the document READ ONLY:
     no Edit / Delete buttons; show Cancel only when POSTED.

7. LINKS BETWEEN DOCUMENTS AND THE BLOCKS
=====================================================================
7.1 Quotation -> Invoice (convert-to-invoice)
  - Only an ACCEPTED quotation. The invoice copies supplier, branch, lines
    (unitPrice -> unitCost), discount and tax; currency = the default (rate 1).
  - The quotation becomes CONVERTED (convertedToInvoiceId); the invoice shows
    convertedFromQuotation { id, code }. Show both as links.
  - The invoice is a normal DRAFT: edit payment, supplier invoice number,
    expiry dates... before posting.
  - DELETE of that DRAFT invoice frees the quotation (same transaction): it
    goes back to ACCEPTED, convertedToInvoiceId = null, and can be converted
    again (a new PI number).
  - CANCEL of the POSTED invoice does NOT: the quotation stays CONVERTED and
    still points to the cancelled invoice (the history is kept).

7.2 Invoice -> Returns
  - GET /purchase-invoices/:id lists purchaseReturns [{ id, code, returnDate, status, netTotal }].
  - GET /purchase-invoices/:id/returnable gives, per invoice line (in the line's
    unit): quantity (bought), returnedQuantity (POSTED returns only), remainingQuantity.
  - A return line points to an invoice line with purchaseInvoiceLineId.
    Product, unit, price, discount and tax come from the invoice.

7.3 The blocks (what the server refuses, and the error)
  - Cancel an invoice that has a POSTED return
      -> 400 BAD_REQUEST field "status" -> "ألغِ المرتجع أولًا"
  - Return more than bought minus already returned
      -> 400 QUANTITY_EXCEEDED field "lines.N.quantity" -> "الكمية أكبر من المسموح بإرجاعه"
  - Post a return / cancel an invoice when the goods are not in the warehouse
      -> 400 INSUFFICIENT_STOCK field "lines.N.quantity" -> "الكمية المتاحة في المخزن غير كافية"
  - Delete a currency used by purchase invoices
      -> 400 BAD_REQUEST "Currency is used by N purchase invoice(s) and cannot be deleted"
         -> "لا يمكن حذف العملة لأنها مستخدمة في فواتير شراء"
  - Delete / unset the default currency
      -> 400 BAD_REQUEST field "isDefault" -> "اجعل عملة أخرى أساسية أولًا"
  - Change a product's primary unit once it has stock movements or product units
      -> 400 BAD_REQUEST field "primaryItemUnitId"
         -> "لا يمكن تغيير الوحدة الأساسية بعد استخدام الصنف (له حركات مخزن أو وحدات)"
  - SERVICE items (خدمي): can't be put in a warehouse (400 field "productId");
    a product can't become SERVICE while it is in a warehouse (400 field "itemType");
    SERVICE lines on invoices / returns are allowed but never move stock.
  - Delete an item unit used by a product unit -> 400 BAD_REQUEST
      "ItemUnit is used by N product unit(s) and cannot be deleted"

9. HOW THE SERVER COMPUTES THE TOTALS
=====================================================================
  lineTotal     = quantity x price - line discount                   (4 decimals)
                  price = unitPrice (quotation) / unitCost (invoice, return)
                  line discount = discountPercent % of it, OR a fixed discountValue (not both)
  subTotal      = sum of lineTotal                                   (2 decimals)
  discountValue = subTotal x discountPercent / 100
                  (if discountPercent is 0 or not sent: the fixed discountValue you send)
  taxValue      = (subTotal - discountValue) x taxPercent / 100
  netTotal      = subTotal - discountValue + taxValue
  Rounding: half up.

  Brush invoice: 10 x 150 = 1500; discount 10% = 150; tax 14% of 1350 = 189; net 1539.
  Brush return: 2 x 150 = 300; discount 30 (the invoice's share: 300 x 150 / 1500);
                tax 14% of 270 = 37.80; net 307.80.

  Invoice payment:   CASH   -> paidAmount = netTotal, remainingAmount 0
                     CREDIT -> paidAmount 0 .. netTotal (default 0), remainingAmount = netTotal - paidAmount
  Return refund:     refundAmount 0 .. netTotal (default 0)
  Stock cost of one piece when an invoice is POSTED (tax not included):
     stockUnitCost = lineTotal x (1 - discountValue / subTotal) x exchangeRate / baseQuantity
     brush: 1500 x 0.9 x 1 / 120 = 11.25
  New average after a stock IN: (old qty x old avg + in qty x in cost) / (old qty + in qty)
     brush: (100 x 10 + 120 x 11.25) / 220 = 10.6818
  Stock OUT (return post, invoice cancel) leaves at the current average; the average stays.

  The frontend must NOT send (the server rejects or ignores them):
    - totals: subTotal, taxValue, netTotal, remainingAmount, lineTotal, baseQuantity,
      unitFactor, stockUnitCost  (-> 400 "property X should not exist")
    - codes and statuses: code, status (status changes only via the action endpoints)
    - user ids: createdBy, modifiedBy, postedBy, cancelledBy (taken from the token)
    - stock quantities on documents (stock is computed from the lines when posting)
    - on a LINKED return line: productId / itemUnitId / unitCost are ignored
      (taken from the invoice line); discount and tax are ignored (taken from the invoice)
  Limits: quantities, prices and costs max 4 decimals; money (paidAmount,
  refundAmount, header discountValue) max 2; percents 0-100 with max 2 decimals.
  Too many decimals -> 400 VALIDATION_FAILED (the server never rounds your input).
